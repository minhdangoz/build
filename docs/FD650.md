# FD650 front-panel display — shared TX68 + KM7 reference

Both TX68 (H618) and KM7 (S905Y4) carry the same physical FD650 4-digit
7-segment module, but on completely different kernel drivers:

| | TX68 | KM7 |
|---|---|---|
| Driver | Out-of-tree chardev, ported from vendor Android BSP (`drivers/vfd/fd650.c`) | Amlogic LED-class driver, linked into the aggregate `amlogic-led.ko` module (`common_drivers/drivers/led/fd650.c`, `CONFIG_AMLOGIC_LEDS_FD650=y`) |
| Interface | `/dev/fd650_dev`, 6-byte write (4 chars + dot_fg + brightness) | `/sys/class/leds/fd650/fd650_display`, text write `"colon_on text"` |
| Brightness | 8 levels, driver-native | 8 levels through the LED-class `brightness` attribute |
| Charset | 58 chars (digits, letters, space, `-`, `_`, `.`, `*`=degree) | Hex digits plus space and `*`=degree |
| Boot-time display | U-Boot vendor "8888" (unchangeable, secure-boot signed), then kernel probe "0001" | U-Boot: unknown/not investigated. Kernel probe: "0001" |

Full hardware detail per board: `docs/TX68_HARDWARE.md` §11.2,
`docs/KM7_HARDWARE_SPECS.md` "Front-panel display (FD650)".

## Shared userspace tooling

`fd650ctl` and `fd650-clock-rotate`
(`packages/bsp/common/usr/local/bin/`) work on **both** boards by detecting
the backend at runtime (`detect_backend()` in `fd650ctl`) — one script, not
a per-board fork, so a bug fixed once is fixed on both boards. Do not
duplicate this logic into a board-specific copy; see
`multi-board-shared-config-discipline` in project memory for why (a shared
identity-config bug already bit this project once).

```bash
fd650ctl time                       # show current HH:MM (blinking colon)
fd650ctl temp                       # show CPU temperature (with ° symbol on TX68)
fd650ctl show ABCD --dot            # arbitrary 4-char text, colon on
fd650ctl show TEST --brightness 5
fd650ctl off                        # blank the display
fd650ctl brightness N               # show "8888" at level N (1-8) -- for testing
fd650ctl test-brightness            # cycle all 8 levels, 3s each
fd650ctl daemon start|stop|restart|status   # control the rotation service
fd650ctl help
```

No `sudo` needed for any of the above as long as the invoking user is in
the `video` group (the desktop user is, by default) — see the udev/polkit
rules below.

### Default behavior

The rotation service (`tx68-fd650-clock.service` / `km7-fd650-clock.service`,
both `ExecStart=/usr/local/bin/fd650-clock-rotate`) starts the instant the
fd650 device appears (device-triggered systemd activation, not after the
whole of `systemd-udev-settle` — verified ~15s post-boot on both boards) and:

1. Shows minutes:seconds since boot (blinking colon) as a live "still
   alive" counter, for as long as `timedatectl show -p NTPSynchronized`
   reports anything other than `yes`.
2. The instant it reports `yes` (== the box actually has working
   internet), switches to rotating real clock (3s) ↔ CPU temperature (2s).
   Falls back to the boot-progress counter automatically if NTP sync is
   ever lost again.

Override timing/brightness via `FD650_BRIGHTNESS` / `FD650_TIME_SECONDS` /
`FD650_TEMP_SECONDS` environment in the respective systemd unit.

### No-sudo access — how it's wired

- **udev**: `99-fd650.rules` (TX68, misc chardev, plain `GROUP=`/`MODE=`
  works) / `99-fd650-km7.rules` (KM7, LED-class sysfs device — `MODE=`/
  `GROUP=` on the rule line do **not** apply to sysfs attribute files for a
  device with no `/dev` node, confirmed on real hardware; `RUN+=` chmod/
  chgrp is what actually works). Both also `TAG+="systemd"` so systemd
  generates a `.device` unit to trigger the rotation service from.
- **polkit**: `packages/bsp/common/49-fd650-clock.rules` grants `video`
  group members `org.freedesktop.systemd1.manage-units` scoped to exactly
  `tx68-fd650-clock.service` and `km7-fd650-clock.service` (not systemd
  control in general — that would be far too broad a grant for a
  device-permission group).

## Known bugs fixed this session (read before touching `raw_write()` again)

1. **`printf` octal-escape bug (TX68, but same class of bug possible
   anywhere)**: `printf '%s\%s\%s' text dot_oct brightness_oct` does
   **not** work — `\NNN` escapes are only interpreted by `printf` when they
   are literal characters in the *format string*, not when they arrive via
   a separate `%s`-substituted argument. The driver only reads 6 bytes
   regardless, so the broken version silently fed garbage into
   `dot_fg`/`brightness`, which always fell through to the driver's
   `default:` brightness case — every requested level looked identical.
   Fixed by building the format string via bash double-quote interpolation
   (`printf "%s\\${dot_oct}\\${brightness_oct}" "${text}"`), which makes the
   escapes literal *before* printf ever parses the string.
2. **`xargs grep -l cpu` + `pipefail` (KM7's `soc_thermal` zone has no
   "cpu" in its name)**: piping through `xargs`, then having `xargs` itself
   exit 123 (its own "at least one invocation failed" convention, not
   bash's) when the wrapped `grep` finds nothing, then having `pipefail`
   propagate that 123 and abort the whole script under `set -e`. Fixed by
   replacing the `xargs`/pipe chain with a plain `for` loop + `if grep -q`
   (conditions inside `if` are exempt from triggering `errexit` regardless
   of what they return).
3. **`grep -q` + `pipefail` SIGPIPE (in `service_name()`)**: `cmd | grep -q
   pattern` can report pipeline failure under `pipefail` even when `grep`
   *does* match, because `grep -q` exits the instant it finds a match,
   which can SIGPIPE the still-writing upstream command — pipefail then
   reports that signal-kill exit status for the whole pipeline instead of
   grep's real (successful) one. Fixed by capturing command output into a
   variable first, then `grep <<< "${var}"` (no live pipe between two
   processes to race).
4. **`die()` inside a command substitution doesn't abort the caller**:
   `unit="$(service_name)"` where `service_name` calls `die` (which calls
   `exit 1`) only kills the subshell created by `$(...)` — the assignment
   just receives an empty string, and the *caller* keeps running with that
   empty value (`systemctl stop ""` → "Failed to mangle name"). Any
   function meant to be used inside `$(...)` must `return` a non-zero
   status instead of calling anything that itself calls `exit`; check the
   result at the call site (`unit="$(fn)" || die ...`).
5. **TX68 kernel patch existed but was never selected**: sunxi 6.18 uses
   `patch/kernel/archive/sunxi-6.18/series.conf` as an explicit allow-list.
   `drv-vfd-add-fd650.patch` was present on disk but absent from that file, so
   it was never applied and `olddefconfig` silently discarded `CONFIG_FD650`.
   The patch is now in `series.conf`, uses normal git patch headers, and its
   Kconfig help syntax is valid for Linux 6.18. Acceptance proof is the
   packaged `drivers/vfd/fd650.ko` with alias `oranth,fd650` and
   `CONFIG_FD650=m` in the packaged config.

## KM7 kernel status

`common_drivers/drivers/led/fd650.c` is linked into the KM7
`amlogic-led.ko` aggregate module by `CONFIG_AMLOGIC_LEDS_FD650=y`.
Patch `0009-leds-fd650-wire-led-class-brightness-control.patch`
connects the LED-class `brightness` attribute to the FD650 system-control
command, preserves the selected level across display writes, and maps LED
level 0 to display-off. Levels 1–8 now have the same meaning as TX68.

Patch `0010-leds-fd650-align-display-semantics-with-tx68.patch` removes the
three remaining KM7 differences that affected shared userspace: it stops
forcing unrelated decimal points, maps `*` to the same `0x63` top-half degree
glyph used by TX68, and displays `0001` after a successful direct-GPIO probe.
Therefore the shared temperature string is exactly `50*C` on both boards.
